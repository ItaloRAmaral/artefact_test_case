# Plan: task status (to do, doing, done)

| Field   | Value                                                                                                                                                                                                                                     |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Status  | Done                                                                                                                                                                                                                                      |
| Date    | 2026-11-20                                                                                                                                                                                                                                |
| Request | "Como é uma lista de tarefas, precisamos saber se esta em todo, fazendo ou feito. Vamos adicionar isso." (the user knows it is beyond the spec)                                                                                           |
| Context | `docs/SPEC.md` §2 (task model: "pelo menos" the four fields, so more are allowed) and §3 (list, form, feedback states); DECISIONS D-06, D-07, D-13, D-20, D-21, D-25, D-28, D-29, D-34, D-35; `.claude/rules/backend.md`, `code-style.md` |

**Goal:** every task has a status (`todo`, `doing`, `done`), shown as a colored badge on its card, changed from the card in one click or in the form, and usable as a list filter.

**Architecture:**

- **Domain:** the status is part of the `Task` entity, which guards it like its other invariants. A new use case, `ChangeTaskStatus`, backs a new procedure, `task.changeStatus`, for the card.
- **Contract:** `create`, `update` and the list filter carry `status`.
- **Shared values:** the allowed values are defined once in `src/shared/tasks/task-statuses.ts` and used by the entity, the Zod schemas and the client.

## Global constraints

- **Values:** `'todo' | 'doing' | 'done'` (the user's "todo, fazendo ou feito"). UI labels: `To do`, `Doing`, `Done`, defined once on the client.
- **Default:** a new task starts in `todo`.
- **Transitions:** any status can move to any other. The user asked for no rule, so none is invented.
- **Errors:** an invalid status is a domain error with a literal code, `TASK_STATUS_INVALID`, translated in `init.ts` to `BAD_REQUEST` (D-07, D-25). The Zod `z.enum` rejects it first at the edge.
- **Contract rules:** every procedure input is strict (unknown keys rejected); outputs are built field by field (`toTaskDto` gains `status`).
- **List order:** newest first (D-12); the status does not change it.
- **Dependency rule:** `src/server/domains/` may import only plain constants from `src/shared/tasks/` (`task-limits.ts` and now `task-statuses.ts`); `backend.md` is updated to say so.

## Decisions with the user

| Question                     | Answer                                                                                                 | Date       |
| ---------------------------- | ------------------------------------------------------------------------------------------------------ | ---------- |
| Where is the status changed? | On the card (one control, saved at once, with loading and feedback) and in the create/edit form        | 2026-11-20 |
| How does the list show it?   | The same list (newest first, infinite scroll, filters) with a colored badge per card; no kanban board  | 2026-11-20 |
| Filter by status?            | Yes: `Status: All / To do / Doing / Done` in the sticky bar, on the server, in the URL, reset by Clear | 2026-11-20 |

Decided in this plan, for the user to confirm on approval:

- **The card's badge is the control.** It is a `<select>` styled as a colored pill. A separate badge next to a select would show the same value twice.
- **`task.update` requires `status`.** Like `title`, the form always sends it, so an update is a full replacement of the content. An optional `status` would mean "keep it", while an omitted `description` means "clear it" (D-29): two meanings in one input. Only our form and the e2e tests call `update`.
- **The card uses its own procedure, `task.changeStatus({ id, status })`.** It does not send the whole task through `update`: a status change must not overwrite a title edited elsewhere, and backend.md asks for one use case per operation.

## Review focus

- **Default:** `create` without `status` gives `todo`; the form also defaults to `To do`.
- **Same status:** changing to the current value is allowed and saves (no error, no special case).
- **Invalid status:**
  - At the edge: `{ status: 'archived' }` or `''` is rejected by Zod, `BAD_REQUEST` with `fieldErrors.status`.
  - In the domain: `create` and `changeStatus` reject a value outside the set with `TASK_STATUS_INVALID`, whatever the caller. `restore` trusts stored snapshots, as it does for the title (D-06).
- **Missing task:** `changeStatus` for a deleted id → `NOT_FOUND`; the card shows `This task no longer exists.` in the toast and the list refetches, so the row disappears.
- **Card under a status filter:** with `Status: To do`, moving a task to `Doing` makes it leave the list after the refetch (like a save, D-34 decision).
- **Quick double change:** every status control is disabled while a change is pending and until the list has refetched (the delete pattern of D-28), so two changes never race.
- **Delete and status at once:** delete and status changes have separate mutations. Each one disables only its own controls; both refetch the list.
- **Hand-edited URL:** `?status=archived` or `?status=todo&status=done` is dropped by `readTaskListFilter`, the same as the other keys (D-34).
- **Hydration:** the status comes from the server data, so the SSR HTML and the first client render show the same badge; no zone dependence.
- **Old snapshots in a running dev server:** tasks created before this change exist only in the memory of a dev server started before it. They have no `status`, so restart `pnpm dev` once. No migration code, because production always starts empty (D-05); the README notes it under "Run".

| XSS                            | Labels are fixed strings rendered as React text                                                                           | —                                                                                            |
