## Test strategy for the whole

- **Levels (D-08):** unit tests carry the server logic (sub-plans 2 and 3) and the error-message module (4); component tests carry the form and list behavior (4, 5, 6); Playwright proves the flows across the stack (smoke in 1, list and delete in 4, create/edit in 5, scroll in 6), without repeating edge cases the unit tests prove.
- **Production build for SSR:** every e2e test runs against `pnpm build && pnpm start` (D-18), because `next dev` renders every request and hides a page prerendered at build time.
- **Coverage:** at least 90% of lines and branches in `src/server/**`, enforced by `pnpm test:coverage` from sub-plan 1 on; each sub-plan leaves the gate green.
- **Determinism:** fixed clock and sequential IDs in unit tests; e2e tests create their own data with unique titles and never assume an empty list, because the in-memory repository is shared by the running server.
- **Every requirement of the spec maps to a test:**

| --- | --- |

## Security

The app has no authentication and no database (D-09), so session, authorization and SQL injection threats do not apply.

| Threat | How it is handled | Sub-plan |
| --- | --- | --- |
| Mass assignment (client sets `id` or `createdAt`) | strict input schemas reject unknown keys; the server sets both | 3 (test), 2 (`createdAt`/`id` from ports) |
| Unbounded input growing memory | length caps on `title`, `description`, `id` and `cursor`; page-size cap | 2 (values and entity), 3 (schema tests) |
| XSS through task text | text rendered by React as text, never `dangerouslySetInnerHTML` | 4 (test), 5 |
| Internal details in errors | one translation point; unexpected errors become `INTERNAL_SERVER_ERROR` without message | 3 (test) |
| Server code in client bundles | `server-only` on the modules that wire or expose the server (D-13); the build fails on a client import | 1 (setup), 3 |
| Secrets in the repository | none needed: no external service, no keys | — |

## Interfaces between sub-plans

Fixed here so each sub-plan can be detailed alone.

**Shared limits (2 → 3, 5).** `src/shared/tasks/task-limits.ts` exports the limits as plain constants with no imports (D-13). Sub-plan 2 creates it, with the values asked to the user; the entity (2), the schemas (3) and the form through the schemas (5) use it.

**Back-end core → tRPC layer (2 → 3).** `tasks-module.ts` exports `createTasksModule(deps: { repository: TaskRepository; clock: Clock; idGenerator: IdGenerator })`, returning `{ createTask, listTasks, getTask, updateTask, deleteTask }`, each a use case with `execute(input)`. Use cases return `Task` entities (or a page `{ items: Task[]; nextCursor: string | null }` for `ListTasks`) and throw `DomainError` subclasses with a literal `code`: `TASK_NOT_FOUND`, `TASK_TITLE_REQUIRED`, `TASK_CURSOR_INVALID` (a cursor that cannot be decoded), plus any limit code sub-plan 2 defines. Which layer encodes and decodes the cursor, and who applies the default page size, is decided in sub-plan 2.

**tRPC contract (3 → 4, 5, 6).** Router `task`, schemas in `src/shared/tasks/task-schemas.ts`:

| Procedure | Kind | Input | Output | Expected errors |
| --- | --- | --- | --- | --- |
| `task.list` | query | `{ cursor?: string \| null; limit?: number }` | `{ items: TaskDto[]; nextCursor: string \| null }`, newest first | `BAD_REQUEST` (limit out of range: field issue; undecodable cursor: `TASK_CURSOR_INVALID`) |
| `task.getById` | query | `{ id: string }` | `TaskDto` | `NOT_FOUND` (`TASK_NOT_FOUND`) |
| `task.create` | mutation | `{ title: string; description?: string }` | `TaskDto` | `BAD_REQUEST` (field issues) |
| `task.update` | mutation | `{ id: string; title: string; description?: string }` | `TaskDto` | `BAD_REQUEST`, `NOT_FOUND` (`TASK_NOT_FOUND`) |
| `task.delete` | mutation | `{ id: string }` | `{ id: string }` | `NOT_FOUND` (`TASK_NOT_FOUND`) |

- `TaskDto = { id: string; title: string; description: string | null; createdAt: string }` (`createdAt` in ISO 8601, D-11).
- The shared schemas trim `title` and `description`. A whitespace-only title fails as a `title` field issue; a blank or omitted `description` is stored as `null`.
- `task.update` replaces `title` and `description` together: an omitted `description` clears it to `null`. It never changes `id` or `createdAt`.
- `task.getById` is not one of the four CRUD operations the spec lists; the edit page needs it to load the task when opened directly by URL or after a refresh.
- Every input schema is strict: unknown keys are rejected (D-06).
- Domain code → tRPC code: `TASK_NOT_FOUND` → `NOT_FOUND`; `TASK_TITLE_REQUIRED`, `TASK_CURSOR_INVALID` and limit codes → `BAD_REQUEST`.
- Error shape the UI reads: `error.data.code` (tRPC code) and, for a domain error, `error.data.domainCode`; for validation failures, `error.data.fieldErrors: Record<string, string[]>`. One module maps these to messages (D-07); an unknown code or a missing `data` (network failure, server down) maps to a generic message. Built and tested in sub-plan 4, reused by 5 and 6.
- `cursor` is opaque to the client: it passes back the `nextCursor` it received.

**Pages (4, 5, 6).** Routes: `/` (list), `/tasks/new` (create), `/tasks/[id]/edit` (edit). Sub-plans 4 and 6 share the list query (`task.list` through TanStack Query's infinite query), so the SSR prefetch, the delete update, the invalidation after a save and the scroll all act on the same cache entry.
