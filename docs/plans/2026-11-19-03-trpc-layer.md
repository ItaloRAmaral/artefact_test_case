**Goal:** the five `task` procedures served at `/api/trpc`, with strict shared Zod schemas, explicit output objects and one error translation point, unit-tested through `createCaller` and proved over HTTP on a production build.

**Architecture:** the input schemas live in `src/shared/tasks/task-schemas.ts` (the form reuses them in sub-plan 5). Everything tRPC lives in `src/server/adapters/` (D-23): `trpc/init.ts` (context type, error formatter, domain-error middleware), `trpc/app-router.ts`, `trpc/handler.ts` (the fetch adapter with its options) and `controllers/task/` (the procedures and the output mapping). The repository singleton stays in the composition root `src/server/tasks-module.ts` on `globalThis` (D-05). The Next.js route `src/app/api/trpc/[trpc]/route.ts` only re-exports the handler. The React side (query client, provider with `httpLink`, server options proxy, hydration) moves to sub-plan 4, its first user, so this sub-plan ships nothing untested.

## Global constraints

- Versions (D-19: newest release at least 7 days old on 2026-11-19, checked with `pnpm view <pkg> time`; D-02's 11.29.5 and 5.108.0 were too fresh): `@trpc/server` 11.28.0, `zod` 4.6.7, pinned exactly. For sub-plan 4: `@trpc/client` and `@trpc/tanstack-react-query` 11.28.0, `@tanstack/react-query` 5.107.1 (peer `^5.106.0`). No transformer (D-11: `createdAt` is an ISO string).
- Contract (roadmap "tRPC contract", D-15): procedures `task.list`, `task.getById`, `task.create`, `task.update`, `task.delete`; `TaskDto = { id: string; title: string; description: string | null; createdAt: string }`; `delete` returns `{ id }`; `update` with `description` omitted clears it to `null`. Addition (user decision): `task.list` also accepts `direction?: 'forward' | 'backward'` and ignores it, because tRPC's infinite query sends `{ ...input, cursor, direction }` (`@trpc/tanstack-react-query` 11.28.0 source, `dist/utils-*.mjs`).
- Limits (D-20, `src/shared/tasks/task-limits.ts`): title 1 to 120 after trimming, description up to 1000 after trimming, `id` up to 36, `cursor` up to 84, page size 1 to 50 with default 10.
- Error mapping (roadmap; user decision for storage): `TASK_NOT_FOUND` → `NOT_FOUND`; `TASK_TITLE_REQUIRED`, `TASK_TITLE_TOO_LONG`, `TASK_DESCRIPTION_TOO_LONG`, `TASK_CURSOR_INVALID` → `BAD_REQUEST`; `TASK_STORAGE_FULL` → `CONFLICT` (409).
- Error data on the wire, built field by field: `{ code, httpStatus, path, domainCode, fieldErrors }`. `domainCode` is the `TaskErrorCode` or `null`; `fieldErrors` is `z.flattenError(cause).fieldErrors` for an input validation error, else `null`. Never `stack`; the message of an `INTERNAL_SERVER_ERROR` becomes `'Internal server error'` (the wording of the tRPC error-formatting docs example).
- Transport (user decisions): batching off (`allowBatching: false`; sub-plan 4 uses `httpLink`); an `INTERNAL_SERVER_ERROR` is logged on the server with `console.error` (one explained `no-console` exception), never sent to the client.
- tRPC behavior relied on (trpc.io, read 2026-11-19): a non-`TRPCError` thrown in a procedure becomes `INTERNAL_SERVER_ERROR` with the original error as `cause` and **its message sent to the client, in production too**; `data.stack` is added when `isDev` (default `NODE_ENV !== 'production'`); a failed `.input()` is `BAD_REQUEST` with the validator's error as `cause`; `opts.next()` in a middleware resolves to `{ ok: false, error }` instead of throwing; a caller throws `TRPCError`; adapters take `allowBatching` and `onError({ error, type, path, input, ctx, req })`. The docs do not show a middleware rethrowing a different `TRPCError` after `next()`, nor say whether `errorFormatter` runs for callers: Task 1's tests prove the first, and the wire shape is tested through the fetch adapter, never through a caller.
- Zod 4 (zod.dev, read 2026-11-19): `z.strictObject` rejects unknown keys (`.strict()` is legacy); `z.flattenError(err)` returns `{ formErrors, fieldErrors }` (`err.flatten()` is deprecated); custom messages use `{ error: '...' }`; `.default(v)` short-circuits on `undefined`. The docs do not state whether `.trim()` runs before `.min(1)`: Task 2's whitespace-only title test proves it.
- `CLAUDE.md` hard rules: strict schema in every `.input()`; output objects built field by field; one translation point; no `try/catch` in procedures; every non-type, non-test file under `src/server/adapters/` imports `server-only`; a client component imports only types from `src/server/` (D-26).

## Review focus

- **Whitespace-only title** (`'   '`) → `BAD_REQUEST` with a `title` field issue, like an empty one; the use case never runs.
- **Unknown keys** on every procedure (`id` or `createdAt` on create, `createdAt` on update, an `extra` key on `getById`, `delete` and `list`) → `BAD_REQUEST`; nothing is created or changed.
- **The infinite query's `direction`** (`'forward'`) is accepted by `task.list`.
- **Out-of-range input:** title of 121 characters, description of 1001, `id` of 37, `cursor` of 85, `limit` of 0, 51 or 1.5 → `BAD_REQUEST`. Exactly 120 and 1000 are accepted (proved at the entity in sub-plan 2; the schema uses the same constants).
- **Default page size:** `task.list` with no `limit` returns at most 10 items and a `nextCursor` when an 11th exists.
- **Undecodable cursor within the length cap** → `BAD_REQUEST` with domain code `TASK_CURSOR_INVALID`.
- **Missing task** on `getById`, `update` and `delete` → `NOT_FOUND` with domain code `TASK_NOT_FOUND`.
- **Storage full** on `create` → `CONFLICT` with domain code `TASK_STORAGE_FULL`.
- **Update without `description`** clears it to `null`; `id` and `createdAt` never change.
- **An unexpected error** (a bug) → `INTERNAL_SERVER_ERROR` whose message and data carry neither the original message nor a stack; the server logs it.
- **A batched request** (`?batch=1`) → rejected with `400`.
- **Hot reload in dev:** the repository survives module re-evaluation (`globalThis`, D-05), proved by re-importing `tasks-module.ts` after `vi.resetModules()`.
- **Output:** every procedure returns exactly the contract's fields (no snapshot or entity), with `createdAt` as an ISO string.
